# Service Completion Ideas

## 1. 문서 목적

이 문서는 현재 RAG MVP를 실제로 "완성된 서비스"에 가깝게 만들기 위해 필요한 다음 작업 아이디어를 정리한 문서다.  
다음 스프린트의 후보 작업을 빠르게 고르기 위해 우선순위와 이유를 함께 남긴다.

## 2. 현재 상태 요약

- 유닛 테스트와 모킹 기반 통합 테스트는 확보되어 있다.
- Nest 앱 자체 부팅은 확인됐다.
- `docker compose` 기반 실제 e2e는 시도했고, 외부 의존성 버전 호환 문제를 발견했다.
- 따라서 현재는 "앱 내부 안정화는 시작됐지만, 시스템 수준 운영 완성도는 아직 낮은 상태"로 보는 것이 맞다.

## 3. 가장 먼저 해야 할 작업

### 3-1. 실제 e2e 완료

#### 왜 필요한가

- 현재 서비스의 핵심 가치는 문서 적재와 질의 응답 전체 흐름이다.
- 이 흐름을 끝까지 검증하지 못하면 서비스 완성 여부를 판단할 수 없다.

#### 해야 할 일

- Ollama 버전 호환 문제 해결 후 `health -> ingest -> query` 전체 시나리오 완료
- 텍스트 직접 적재 1건
- 샘플 파일 업로드 1건 이상
- 적재된 근거 기반 질의 응답 1건 이상
- 성공/실패 기준을 문서화

#### 반영 내용

- `docker-compose.yml` 의 Ollama 이미지를 `0.13.3` 으로 상향해 SDK 임베딩 호출과의 호환 기준을 맞췄다.
- Chroma 연동은 현재 서버가 제공하는 v1 HTTP API 기준 어댑터로 정리해 `chromadb/chroma:0.5.5` 환경에서 실제 적재와 조회가 가능하도록 맞췄다.
- `scripts/system-e2e.sh` 를 추가해 `health -> ingest/text -> ingest/files -> query` 실제 흐름을 한 번에 검증할 수 있게 했다.
- `package.json` 에 `npm run test:system-e2e` 스크립트를 추가했다.
- `README.md` 에 실행 절차와 완료 기준을 반영했다.

#### 완료 기준

- `GET /health` 가 `200`
- `POST /ingest/text` 성공
- `POST /ingest/files`에서 최소 1개 이상 성공
- `POST /query` 응답에 `answer`, `citations`, `retrieved` 가 유효하게 포함

### 3-2. Docker/버전 호환성 정리

#### 왜 필요한가

- 실제 e2e 실패 원인이 코드가 아니라 외부 서비스 버전 문제였다.
- MVP라도 외부 의존성 버전이 고정되지 않으면 재현성과 운영 안정성이 떨어진다.

#### 해야 할 일

- `docker-compose.yml` 의 Ollama/Chroma 권장 버전 확정
- SDK 버전과 서버 버전의 호환 기준 정리
- README 실행 절차를 현재 버전에 맞게 갱신
- 모델 pull 절차와 검증 절차 표준화

## 4. 제품 완성도를 높이기 위한 다음 작업

### 4-1. 테스트 체계 확장

#### 아이디어

- `ChunkingService` 단위 테스트 추가
- `QueryService`의 citation 구성 규칙 검증 강화
- `IngestController` multipart 업로드 테스트 추가
- 시스템 e2e를 자동 스크립트 또는 별도 테스트로 고정

#### 기대 효과

- 회귀를 더 빨리 잡을 수 있다.
- 문서 업로드와 응답 근거 형식이 깨지는 문제를 조기에 발견할 수 있다.

### 4-2. 장애 진단 가능성 강화

#### 아이디어

- 적재 요청별 request id 또는 doc id 로깅
- 외부 의존성 실패 시 현재보다 더 구체적인 에러 메시지 반환
- `/health` 에 모델 상태 또는 버전 정보 일부 포함
- 로그에 ingest/query 단계별 소요 시간 기록

#### 기대 효과

- "왜 실패했는지"를 운영 중 더 빨리 알 수 있다.
- 지금처럼 e2e 실패 시 원인 추적 시간이 줄어든다.

### 4-3. 문서 품질과 적재 품질 개선

#### 아이디어

- 파일별 추출 성공률 측정
- OCR 미지원 범위를 명확히 안내
- 문단/페이지 단위 메타데이터를 더 정교하게 저장
- 청크 전략 조정 옵션 도입

#### 기대 효과

- 검색 품질과 citation 품질이 올라간다.
- 사용자가 "왜 이 답이 나왔는지"를 더 잘 이해할 수 있다.

### 4-4. 질의 응답 품질 개선

#### 아이디어

- 프롬프트 품질 개선
- retrieval score 기준 최소 threshold 도입 검토
- 필터 전략 개선
- 답변 길이와 인용 형식 규칙 고도화

#### 기대 효과

- 근거 부족 상황과 충분한 근거 상황을 더 안정적으로 구분할 수 있다.
- 사업기획서 작성 보조 용도에 맞는 응답 일관성이 올라간다.

## 5. 운영 준비 관점에서 필요한 작업

### 5-1. 환경 설정 정리

#### 아이디어

- `.env.example` 와 실제 README의 실행 흐름 동기화
- 개발/테스트/운영 환경 변수 표 분리
- 포트 충돌과 모델 미다운로드 대응 절차 정리

### 5-2. 데이터 관리 전략

#### 아이디어

- 컬렉션 분리 전략 검토
- 프로젝트별 메타데이터 규칙 표준화
- 업로드 원본과 인덱싱 결과의 추적성 확보

### 5-3. 보안과 접근 제어

#### 아이디어

- 내부 사용자 인증
- 프로젝트별 문서 접근 제한
- 민감 메타데이터 마스킹 또는 저장 제한

## 6. 추천 우선순위

1. 실제 e2e 완료
2. Docker/외부 의존성 버전 호환성 정리
3. 시스템 e2e 자동화
4. 로깅/에러 메시지 강화
5. 적재 품질 및 검색 품질 개선
6. 운영 환경 설정과 데이터 전략 정리

## 7. 다음 작업 제안

다음 작업은 아래 순서가 가장 합리적이다.

1. Ollama 버전 문제를 해결한 상태로 실제 e2e를 완료한다.
2. 그 과정을 자동화 가능한 검증 시나리오로 문서화하거나 스크립트화한다.
3. 이후 품질 개선 작업은 `ingest 품질`, `query 품질`, `운영 가시성` 세 축으로 나눠 진행한다.
