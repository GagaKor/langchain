# Service Completion Ideas

## 1. 문서 목적

이 문서는 현재 RAG MVP를 실제로 "완성된 서비스"에 가깝게 만들기 위해 필요한 다음 작업 아이디어를 정리한 문서다.  
다음 스프린트의 후보 작업을 빠르게 고르기 위해 우선순위와 이유를 함께 남긴다.

## 2. 현재 상태 요약

- 유닛 테스트와 모킹 기반 통합 테스트는 확보되어 있다.
- Nest 앱 자체 부팅은 확인됐다.
- `docker compose` 기반 실제 e2e는 시도했고, 외부 의존성 버전 호환 문제를 발견했다.
- 따라서 현재는 "앱 내부 안정화는 시작됐지만, 시스템 수준 운영 완성도는 아직 낮은 상태"로 보는 것이 맞다.

## 3. 가장 먼저 해야 할 작업

### 3-1. 실제 e2e 완료

#### 왜 필요한가

- 현재 서비스의 핵심 가치는 문서 적재와 질의 응답 전체 흐름이다.
- 이 흐름을 끝까지 검증하지 못하면 서비스 완성 여부를 판단할 수 없다.

#### 해야 할 일

- Ollama 버전 호환 문제 해결 후 `health -> ingest -> query` 전체 시나리오 완료
- 텍스트 직접 적재 1건
- 샘플 파일 업로드 1건 이상
- 적재된 근거 기반 질의 응답 1건 이상
- 성공/실패 기준을 문서화

#### 반영 내용

- `docker-compose.yml` 의 Ollama 이미지를 `0.13.3` 으로 상향해 SDK 임베딩 호출과의 호환 기준을 맞췄다.
- Chroma 연동은 현재 서버가 제공하는 v1 HTTP API 기준 어댑터로 정리해 `chromadb/chroma:0.5.5` 환경에서 실제 적재와 조회가 가능하도록 맞췄다.
- `scripts/system-e2e.sh` 를 추가해 `health -> ingest/text -> ingest/files -> query` 실제 흐름을 한 번에 검증할 수 있게 했다.
- `package.json` 에 `npm run test:system-e2e` 스크립트를 추가했다.
- `README.md` 에 실행 절차와 완료 기준을 반영했다.

#### 완료 기준

- `GET /health` 가 `200`
- `POST /ingest/text` 성공
- `POST /ingest/files`에서 최소 1개 이상 성공
- `POST /query` 응답에 `answer`, `citations`, `retrieved` 가 유효하게 포함

### 3-2. Docker/버전 호환성 정리

#### 왜 필요한가

- 실제 e2e 실패 원인이 코드가 아니라 외부 서비스 버전 문제였다.
- MVP라도 외부 의존성 버전이 고정되지 않으면 재현성과 운영 안정성이 떨어진다.

#### 해야 할 일

- `docker-compose.yml` 의 Ollama/Chroma 권장 버전 확정
- SDK 버전과 서버 버전의 호환 기준 정리
- README 실행 절차를 현재 버전에 맞게 갱신
- 모델 pull 절차와 검증 절차 표준화

## 4. 다음 스프린트 아이디어

현재까지의 아이디어는 배포와 안정성 정리에 무게가 있었다.  
다음 스프린트는 기능 확장 관점에서 우선순위를 다시 잡는 것이 더 적절하다.

### 4-1. OCR 지원 추가

#### 왜 먼저 해야 하나

- 현재 MVP는 텍스트 추출 가능한 문서만 처리할 수 있다.
- 실제 업무 문서에는 스캔 PDF, 이미지 기반 문서, 캡처본이 섞여 있을 가능성이 높다.
- 따라서 사용자가 체감하는 적재 성공률을 가장 직접적으로 끌어올릴 수 있는 작업이다.

#### 아이디어

- OCR 대상 파일 유형 범위 정의
- 스캔 PDF와 일반 PDF를 구분하는 처리 흐름 설계
- OCR 수행 후 기존 chunking/metadata 흐름에 연결
- OCR 실패 시 현재보다 구체적인 실패 사유 반환
- OCR 적용 여부와 추출 방식(`native`, `ocr`)을 메타데이터에 기록

#### 기대 효과

- 현재 MVP에서 실패 처리되던 문서 일부를 실제로 적재할 수 있다.
- 파일 업로드 성공률이 올라가고 사용성 개선 폭이 크다.

#### MVP 범위

- 1차 대상은 스캔 PDF 와 이미지 기반 PDF 로 한정
- OCR 엔진은 단일 구현으로 시작하고 다중 엔진 선택은 제외
- 기존 `/ingest/files` 흐름 안에서 OCR fallback 으로만 동작
- OCR 결과는 plain text 로만 저장하고 레이아웃 복원은 제외

#### API 변경

- `POST /ingest/files`
  - 요청 옵션에 `ocrMode` 같은 실행 정책 필드 추가 검토
  - 응답 파일 결과에 `extractionMethod: native | ocr` 포함
- 필요 시 `/health` 응답에 OCR 엔진 준비 상태 포함

#### 완료 기준

- 스캔 PDF 샘플 1건 이상이 `status=ok` 로 적재
- OCR 적용 파일이 메타데이터 또는 응답에서 `ocr` 처리로 식별 가능
- OCR 실패 시 파일별 `reason` 이 구체적으로 반환
- 기존 비 OCR 파일 적재 흐름이 회귀 없이 유지

#### Sprint A 반영 내용

- `ocrMode=auto` 옵션을 통해 스캔 PDF 에 대한 OCR fallback 경로를 추가했다.
- OCR 의존성이 없는 환경에서는 실패 사유를 명시적으로 반환하도록 정리했다.
- OCR 적용 여부를 `extractionMethod: native | ocr` 로 파일 결과와 메타데이터에 남기도록 했다.

### 4-2. 비동기 적재

#### 왜 중요한가

- OCR이 들어가면 적재 시간과 리소스 사용량이 지금보다 커진다.
- 큰 문서나 다중 파일 업로드를 동기 요청으로 처리하면 사용자 대기 시간이 길어지고 타임아웃 위험도 커진다.

#### 아이디어

- 업로드 요청은 job 생성만 수행하고 실제 적재는 비동기 worker 가 처리
- `queued`, `processing`, `completed`, `failed` 상태 정의
- 요청 즉시 job id 반환
- 실패 시 파일 단위와 job 단위 실패 사유 분리
- 향후 OCR, 재색인, 대량 업로드에도 재사용 가능한 적재 파이프라인 구조로 정리

#### 기대 효과

- 긴 적재 요청이 API 응답 시간과 분리된다.
- OCR, 대용량 문서, 다중 파일 처리에 더 적합한 구조가 된다.

#### MVP 범위

- 문서 적재만 비동기화하고 query 는 기존 동기 방식 유지
- 단일 프로세스 내부 job queue 또는 최소 구현 worker 로 시작
- 재시도 정책은 단순 1회 또는 수동 재시도로 제한
- 우선 대상은 `/ingest/files`, 필요 시 `/ingest/text` 는 후순위

#### API 변경

- `POST /ingest/files`
  - 즉시 적재 결과 대신 `jobId`, `status=queued` 반환
- `GET /ingest/jobs/:jobId`
  - 현재 상태, 파일별 진행 현황, 실패 사유 조회
- 필요 시 `POST /ingest/text` 도 동일한 job 구조로 확장 가능하도록 계약 정리

#### 완료 기준

- 다중 파일 업로드 요청이 즉시 `jobId` 를 반환
- 백그라운드 처리 후 최종 상태가 `completed` 또는 `failed` 로 수렴
- 파일 단위 성공/실패 결과를 상태 조회에서 확인 가능
- 긴 적재 작업 중에도 API 기본 응답성이 유지

#### Sprint A 반영 내용

- `/ingest/files` 를 동기 적재에서 비동기 job 생성 방식으로 전환했다.
- 인메모리 job queue 기반으로 `queued -> processing -> completed | failed` 상태 흐름을 추가했다.
- 시스템 e2e 스크립트도 job polling 방식으로 갱신했다.

### 4-3. 삭제 / 재색인

#### 왜 필요한가

- 실제 서비스에서는 잘못 올린 문서, 갱신된 문서, 오래된 문서를 계속 교체해야 한다.
- 현재 구조는 적재 이후 수정 흐름이 부족해 데이터 정합성과 운영 편의성이 떨어진다.

#### 아이디어

- `docId` 기준 삭제 API
- 같은 원본 문서의 재업로드 시 재색인 정책 정의
- 메타데이터 기준 부분 삭제 또는 프로젝트 단위 삭제 전략 검토
- 삭제 후 query 결과에서 제외되는지 검증 테스트 추가

#### 기대 효과

- 문서 lifecycle 관리가 가능해진다.
- 잘못된 적재 결과를 운영 중 바로 복구할 수 있다.

#### MVP 범위

- 우선 `docId` 기준 단건 삭제부터 지원
- 재색인은 "기존 문서 삭제 후 동일 원본 재적재" 방식으로 단순화
- 프로젝트 단위 일괄 삭제는 후순위
- soft delete 없이 vector store 에서 실제 삭제하는 방식으로 시작

#### API 변경

- `DELETE /documents/:docId`
  - 해당 문서와 관련 청크 삭제
- `POST /documents/:docId/reindex`
  - 기존 문서 재색인 또는 신규 job 생성
- 응답에는 삭제/재색인 대상 `docId`, 처리 상태 포함

#### 완료 기준

- 특정 `docId` 삭제 후 query 결과에서 해당 문서 citation 이 제외
- 동일 문서를 재색인하면 최신 결과만 검색에 반영
- 존재하지 않는 `docId` 삭제 시 명확한 에러 또는 no-op 정책이 문서화
- 삭제/재색인 흐름에 대한 테스트가 추가

### 4-4. 적재 상태 조회

#### 왜 필요한가

- 비동기 적재가 도입되면 "지금 어디까지 처리됐는지"를 사용자와 운영자가 확인할 방법이 필요하다.
- OCR 실패, 추출 실패, 임베딩 실패를 같은 적재 실패로만 보면 실제 운영에서 원인 파악이 어렵다.

#### 아이디어

- job id 기준 상태 조회 API
- 파일별 진행 상태와 실패 사유 표시
- 적재 완료 문서 수, 실패 문서 수, 최근 업데이트 시각 반환
- 필요 시 request id, doc id, stage 단위 로그와 연결

#### 기대 효과

- 사용자와 운영자가 적재 결과를 더 명확히 이해할 수 있다.
- 장애 분석과 재시도 판단이 쉬워진다.

#### MVP 범위

- job 단위 상태 조회만 우선 제공
- 파일별 상태와 마지막 에러 메시지까지 노출
- 장기 이력 검색, 통계 대시보드, 필터링 UI 는 제외
- 보존 기간은 단기 운영 확인 목적 수준으로 제한

#### API 변경

- `GET /ingest/jobs/:jobId`
  - `queued`, `processing`, `completed`, `failed` 상태 반환
  - 파일별 `filename`, `status`, `docId`, `reason`, `updatedAt` 포함
- 선택적으로 `GET /ingest/jobs`
  - 최근 job 목록 조회

#### 완료 기준

- 적재 요청 이후 상태 조회만으로 현재 단계와 결과를 판단 가능
- 파일별 성공/실패 문서 수와 사유를 확인 가능
- 실패한 경우 원인이 `extract`, `ocr`, `embed`, `store` 중 어느 단계인지 최소 수준으로 구분
- 비동기 적재와 연결된 문서/테스트/예시 응답이 함께 정리

#### Sprint A 반영 내용

- `GET /ingest/jobs/:jobId` 를 추가해 현재 상태와 파일별 결과를 조회할 수 있게 했다.
- 파일별 `status`, `docId`, `reason`, `extractionMethod`, `updatedAt` 를 함께 반환하도록 정리했다.

## 5. 안정성과 운영 완성도를 높이기 위한 후속 작업

### 5-1. 테스트 체계 확장

#### 아이디어

- `ChunkingService` 단위 테스트 추가
- `QueryService`의 citation 구성 규칙 검증 강화
- `IngestController` multipart 업로드 테스트 추가
- 시스템 e2e를 자동 스크립트 또는 별도 테스트로 고정

#### 기대 효과

- 회귀를 더 빨리 잡을 수 있다.
- 문서 업로드와 응답 근거 형식이 깨지는 문제를 조기에 발견할 수 있다.

### 5-2. 장애 진단 가능성 강화

#### 아이디어

- 적재 요청별 request id 또는 doc id 로깅
- 외부 의존성 실패 시 현재보다 더 구체적인 에러 메시지 반환
- `/health` 에 모델 상태 또는 버전 정보 일부 포함
- 로그에 ingest/query 단계별 소요 시간 기록

#### 기대 효과

- "왜 실패했는지"를 운영 중 더 빨리 알 수 있다.
- 지금처럼 e2e 실패 시 원인 추적 시간이 줄어든다.

### 5-3. 문서 품질과 적재 품질 개선

#### 아이디어

- 파일별 추출 성공률 측정
- OCR 적용 범위와 fallback 규칙 명확화
- 문단/페이지 단위 메타데이터를 더 정교하게 저장
- 청크 전략 조정 옵션 도입

#### 기대 효과

- 검색 품질과 citation 품질이 올라간다.
- 사용자가 "왜 이 답이 나왔는지"를 더 잘 이해할 수 있다.

### 5-4. 질의 응답 품질 개선

#### 아이디어

- 프롬프트 품질 개선
- retrieval score 기준 최소 threshold 도입 검토
- 필터 전략 개선
- 답변 길이와 인용 형식 규칙 고도화

#### 기대 효과

- 근거 부족 상황과 충분한 근거 상황을 더 안정적으로 구분할 수 있다.
- 사업기획서 작성 보조 용도에 맞는 응답 일관성이 올라간다.

## 8. 다음 작업 제안

다음 스프린트는 아래 순서가 가장 합리적이다.

1. OCR을 별도 추출 파이프라인으로 도입할 범위와 지원 문서 유형을 먼저 정의한다.
2. OCR 도입을 전제로 적재 요청을 비동기 job 구조로 전환한다.
3. 그 다음 운영 필수 기능인 `삭제 / 재색인`, `상태 조회`를 붙여 실제 문서 lifecycle 을 완성한다.
4. 이후 안정성 강화 항목은 `테스트`, `로깅`, `검색 품질` 순으로 보강한다.
